# ProbeEP 实验大纲

本大纲描述 evaluation experiment，而不是论文配图清单。这里的一个 `Fig_XX` 对应 FAST
或 LoongX Evaluation 中的一个实验小节：围绕一个问题运行一组受控实验，并从性能、机制、
资源代价和边界等多个角度给出证据。

## 0. Base Case

所有实验从 `markdown/14_专用测试拓扑-EP32-1Plane.md` 的完整配置出发：

- DSV3 代表性 forward：2 个 MoE layer、2 个 microbatch、4096 tokens/rank/microbatch；
- hidden 7168、FFN 2048、256 logical experts、每 rank 8 个连续 master、top-k 8；
- EP32：4 servers × 8 GPUs，1 plane，8 rails，4 spines；
- scale-out 400 Gbps，server-local fabric 7200 Gbps，padding quantum 128；
- Dispatch FP8、Combine BF16、expert weight BF16；
- Gate 使用 `raw_receive_cdf`、seed 17、raw layer 0/1；其来源是 decode-derived empirical
  receive distribution，只能称为 quota-matched empirical workload；
- baseline 为 NCCL、DeepEP、EPLB、MoonEP，创新算法为动态闭环 ProbeEP；
- H20 是默认计算点，H100 是 compute/network balance 对照点。

## 1. 统一实验纪律

1. 同一 case 内所有算法使用相同 Gate assignment digest、模型 DAG 语义、计算 profile、
   topology、transport 和 stream schedule。
2. ProbeEP 主结果使用单个 HTSim PID 中的 observation/update/append 闭环；static ProbeEP
   只能用于结构检查，不能代替动态结果。
3. 端到端主指标是最终 DAG makespan 和有效 token throughput。task FCT sum 只能描述总
   work，不能当 critical-path breakdown。
4. 同时报告收益和代价：compute padding、server/rank imbalance、remote replica、moved
   routes、weight RDMA、endpoint load、overlap 和 queue/link hotspot。
5. Weight RDMA 的 wire bytes 只统计 scale-out leg 一次；`max(TX,RX)` 是单 endpoint
   footprint，禁止跨 rank 再求和冒充 wire bytes。
6. 合成 Gate 与 raw distribution 分开标注；quick/smoke 与 full 数据分开标注。
7. 每个结果保留结构化数据、源运行路径、完整命令、seed、assignment digest 和失败 case。
8. 实验服务器共 128 个 CPU cores；每个 HTSim 仿真按 1 core 运行，全局最多并发 100 个
   HTSim 进程。CPU 0--99 用于仿真，CPU 100--127 留给构建、采集、压缩、绘图和系统，
   不能为了缩短 sweep 时间突破该资源上限。

## Fig_01 End-to-End Performance

**核心问题。** 在相同 prefill/训练 forward workload 下，ProbeEP 是否比通信优化、持久
布局和 server-local replication 更短？这一收益是否同时存在于不同 compute/network
balance？

**不变量。** Base Case 的 Gate、EP32/1Plane、两层两 microbatch、transport 与 stream
语义。

**改变因素。** 算法，以及 H20/H100 两类计算 profile。主 case 不扫描其他参数，保证
五算法结论干净。

**组内实验。**

- E1-a：五算法绝对 makespan 与有效 token throughput；
- E1-b：相对最强 baseline 的 speedup，而不是只相对最弱 NCCL；
- E1-c：H20/H100 上算法排序和收益稳定性；
- E1-d：每个 case 的 task count、logical bytes 和失败状态作为审计数据，不作为性能替代。

**要支持的结论。** 通信优化减少 token movement，MoonEP 式本地复制进一步降低 rank
拖尾，但 ProbeEP 通过跨 server execution placement 消除剩余 server-level compute tail。

**反证条件。** 若 ProbeEP 只在 H20 有效、H100 上 weight traffic 抵消收益，应如实把
compute/network ratio 写成适用边界。

## Fig_02 Mechanism Analysis

**核心问题。** ProbeEP 为什么快，收益是否来自真实的 padded-compute reduction，而不是
隐藏网络债务？

**不变量。** 完全复用 Fig_01 Base Case 和 assignment digest，不增加新的 workload。

**组内实验。**

- E2-a：同一 Gate 在 expert、rank、server 三层形成的 imbalance；
- E2-b：原始 placement、EPLB、MoonEP 和 ProbeEP 的 before/after rank 与 server load，
  直接展示 local-replication ceiling；
- E2-c：ProbeEP 的 baseline、planned、admitted server padded routes，区分 planner
  opportunity 与 NIC admission 后真正落地的收益；
- E2-d：planned/admitted/deferred intents、remote replicas、每 replica moved routes；
- E2-e：remote Weight RDMA、local Weight movement、token bytes、per-endpoint load 和
  compute/network overlap；
- E2-f：关键层/关键 microbatch 的执行时间线，验证 per-source-rail Weight 完成后即可释放
  对应 Dispatch，而不是等待全局 Weight barrier。

**要支持的结论。** local replication 可以改善 server 内 rank balance，但无法改变 server
aggregate lower bound；ProbeEP 用受控的跨 server weight movement 换取更大的 padded
compute saving，并把多数额外网络工作隐藏在可测 overlap window 中。

## Fig_03 Feedback and Adaptivity

**核心问题。** NIC headroom 随 layer、microbatch 和 overlap compute kind 改变时，在线
反馈能否选择比固定预算更合适的迁移量？

**不变量。** Base Case 模型与拓扑。为观察时序可增加 layer 数，但每层 Gate 来源、顺序和
seed 必须记录。

**改变因素。** controller mode、初始/固定 budget、目标 overlap ratio、负载变化顺序。

**组内实验。**

- E3-a：Attention/MoE 两条状态链各自的 observed `N/C` 与 target；
- E3-b：budget before/after、unclamped target 与 endpoint hard cap；
- E3-c：每个 observation 的 planned/admitted/deferred intents、moved routes 和 RDMA bytes；
- E3-d：零迁移、固定保守、固定中等、固定激进和 feedback 的 makespan/迁移代价 Pareto；
- E3-e：构造负载突变，检查控制方向、收敛趋势和两条链是否串扰。

**要支持的结论。** 固定保守值错失 compute opportunity，固定激进值暴露网络成本；
feedback 根据真实 overlap 改变 admission，且不会裁剪 token baseline。

## Fig_04 Workload Sensitivity

**核心问题。** ProbeEP 是否只对当前 raw Gate 有效，还是对不同倾斜结构、负载规模和时间
变化都保持合理行为？

**不变量。** 默认使用 Base Case hardware/topology；每个 sensitivity 只改变一个 workload
维度。主对照至少包含 MoonEP 和 ProbeEP，关键点补齐五算法。

**改变因素。**

- Gate family：balanced、uniform、UltraEP-style rank Zipf、FAST-style source-expert
  matrix、raw receive CDF；
- skew strength：用实测 rank/server max-to-mean 作为横轴，而不是 provider 名称；
- layer/seed：覆盖 raw layer 与多个 synthetic seeds，报告分布而非挑最佳点；
- load volume：tokens/rank、top-k、microbatch/layer depth；
- temporal behavior：热点稳定、层间漂移和突变。

**组内实验。**

- E4-a：speedup 随 baseline server imbalance 的变化；
- E4-b：接近均衡时 admitted replicas/weight bytes 是否自动接近零；
- E4-c：token volume 增大时，固定 expert copy cost 是否被更多 useful routes 摊销；
- E4-d：不同 layer/seed 下的中位数、尾部和失败点；
- E4-e：热点切换时 feedback 的响应及遗留副本是否造成负收益。

**要支持的结论。** ProbeEP 的收益与可消除的 server-level compute skew 相关，而不是与某
个 Gate generator 名字相关；均衡输入应自然退化，极端倾斜最终受 NIC budget 限制。

## Fig_05 Hardware Sensitivity

**核心问题。** “通信换计算”的收益区域如何随硬件 balance 和 expert state cost 改变？

**不变量。** Base Case workload、assignment 和 topology。

**改变因素。** GPU compute profile、scale-out NIC rate、server-local fabric rate、expert
state bytes/precision、weight chunk size。先做单因素，再对 compute × NIC 做必要的二维
交叉。

**组内实验。**

- E5-a：不同 compute profile 下 MoonEP/ProbeEP 的 makespan 与 speedup；
- E5-b：NIC rate 变化时 admission、endpoint utilization 和 exposed migration time；
- E5-c：local/scale-out bandwidth ratio 变化时 gather/scatter 与 RDMA 各自的瓶颈转移；
- E5-d：expert state scale 与 tokens/replica 的摊销关系；
- E5-e：compute × NIC 的 operating region，标出无收益或主动零迁移区域。

**要支持的结论。** compute 较慢、NIC headroom 较多、每个副本承载更多 routes 时更有利；
专家状态过大或网络已满时，ProbeEP 应少迁移而不是强行复制。

## Fig_06 Topology and Scale Sensitivity

**核心问题。** local-replication ceiling 和 ProbeEP 的收益是否依赖当前 4×8 EP32/1Plane
组织？

**不变量。** 每个规模内保持相同的 per-rank workload 语义和算法公平性。raw Gate 只用于
兼容 EP32 的点；跨 EP scale 使用合成 Gate，并匹配 measured imbalance。

**改变因素。** GPUs/server 与 server count、EP size、plane/rail 数、spine/path diversity、
L0-L1 bundle 和 oversubscription。

**组内实验。**

- E6-a：固定 EP32、改变 GPUs/server，观察 server boundary 对 MoonEP ceiling 的影响；
- E6-b：EP size/server count 增长时 makespan、speedup、replica count 和 endpoint bytes；
- E6-c：plane/rail/path diversity 改变时 peak link load 与 tail FCT；
- E6-d：oversubscription 增大时 controller 是否降低 admission；
- E6-e：每个 server pair 的 rail load spread，验证 pair-aware chunk placement。

**要支持的结论。** server 越多，单纯 local replication 越容易留下 aggregate skew；
ProbeEP 的收益必须与拓扑 headroom 一起解释，不能把额外 weight traffic 当作免费。

## Fig_07 Design Ablation

**核心问题。** ProbeEP 的收益来自哪一项设计，哪些模块只是实现复杂度？

**不变量。** Base Case 和同一动态执行路径。消融之间不能混用 static/dynamic runner。

**改变因素与组内实验。**

- E7-a No-Remote：migration budget 为零，退化到 server-local ceiling；
- E7-b Compute-Only：按 compute opportunity 规划，但使用固定激进 admission；
- E7-c Fixed-Conservative / Fixed-Aggressive：去掉 feedback；
- E7-d No-Fine-Grained-Weight：使用单个大 weight chunk，观察 head-of-line blocking；
- E7-e No-Per-Rail-Release：全部 Weight 完成后再释放 Dispatch；
- E7-f No-Pair-Aware-Placement：chunk 不按 server-pair rail load 选择；
- E7-g Full ProbeEP：global planning + feedback admission + local packing + rail pipeline。

每项同时报告 makespan、padded compute、admitted intents、weight RDMA、peak endpoint/link
load 和 overlap。E7-e/E7-f 在实现开关完成前不得用手工数字代替；脚本应显式拒绝缺失的
variant。

**要支持的结论。** global plan 决定“哪里值得迁移”，feedback 决定“当前允许迁移多少”，
rail-aware pipeline 决定“这些通信暴露多少”；三者解决不同问题。

## Fig_08 Overheads and Operating Boundary

**核心问题。** ProbeEP 的控制路径能否扩展，算法在什么 workload/system 区域有净收益？

**证据类型。** reference planner microbenchmark、动态 DAG metadata 统计、analytical
break-even model；三者必须与 packet-level end-to-end 结果分开标注。

**改变因素。** EP size、logical experts、route histogram size、planned intents、weight
chunks、layer depth，以及 token volume × expert state × effective migration rate。

**组内实验。**

- E8-a：global planning、admission/controller、local packing 和 lowering 分阶段耗时；
- E8-b：动态 append、observation parsing、task/metadata 数量与内存增长；
- E8-c：每个 dispatch 的 planner/controller 中位数与尾部；
- E8-d：`compute saving - exposed migration cost` 的 break-even region；
- E8-e：把真实端到端 case 投影到该区域，检查模型能否解释趋势而不是拟合结果。

**结论边界。** Python reference planner 只能说明复杂度趋势。在线 latency、GPU copy
bandwidth、runtime integration 和真实训练迭代开销必须由 Prototype 给出。
