# 测试与日志规范

## 1. 目录责任

```text
tests/   Python 功能测试源码与固定小输入
test_logs/    每次测试运行产生的全部文件
```

测试代码不把生成结果写回 `tests/`。

## 2. 独立运行目录

每次运行创建唯一目录：

```text
test_logs/run_YYYYMMDD_HHMMSS_mprail/
├── 测试说明.md
├── 配置.json
├── 构建.log
├── 汇总.json
├── inputs/
│   ├── *.cm
│   └── *.dag
└── cases/
    └── <case>/
        ├── htsim.log
        └── htsim.dat
```

普通 `htsim_uec` 功能测试不生成 `idmap.txt`，也不生成 `output_metrics/`。
内部对象映射没有当前消费者；若以后恢复旧 `parse_output` 工作流，应通过显式开关
输出，而不是每次仿真无条件写文件。只有显式设置
`HTSIM_LINK_LOAD_SAMPLE=1` 的链路采样案例才在自己的 case/simulation 目录内生成：

```text
output_metrics/
├── link_info.csv
└── link_load_1ms.csv
```

专项测试使用自己的目录后缀，例如：

```text
test_logs/run_<timestamp>_mprail_routing_modes/
test_logs/run_<timestamp>_mprail_source_routing/
test_logs/run_<timestamp>_workload_generator/
test_logs/run_<timestamp>_mprail_visualization/
test_logs/run_<timestamp>_dag_timeline_visualization/
test_logs/run_<timestamp>_dsv3_2layer_4algo_smoke/
test_logs/run_<timestamp>_dsv3_2layer_4algo_full/
```

`测试说明.md` 必须用中文记录：测试目的、拓扑规模、输入、断言、结果和失败诊断。

workload generator 专项目录使用以下结构；它同时保存 generator 产物和 HTSim
消费这些产物的日志：

```text
test_logs/run_<timestamp>_workload_generator/
├── 测试报告.md
├── summary.json
├── 构建.log
├── generated/
│   └── <case>/
│       ├── workload.dag
│       ├── nodes.cm
│       ├── manifest.json
│       ├── task_map.json
│       └── 生成报告.md
└── cases/
    └── <htsim-case>/
        ├── 命令.txt
        └── htsim.log
```

## 3. Python 功能测试

首版测试分为：

1. 拓扑计数：验证 server、rail、L0、L1 数量。
2. 服务器 FullMesh：同服务器流量只走本地路径。
3. 同 rail：跨服务器流量不进入 L1。
4. 跨 rail：路径严格为 `L0 -> L1 -> L0`。
5. Plane 隔离：所有交换链路的两端 plane 一致。
6. Flow hash：多个 flow 能稳定分散到 plane 和 spine。
7. DAG 并发：同 barrier 多 network/compute task 的 barrier 正确。
8. 负例：联合 task、空 task、环、缺失前驱和超时均被拒绝。
9. 静态 connection matrix：不使用 DAG 时仍能完成 flow。
10. 显式路径：同服务器、同 rail、跨 rail 的正反向路径与输入坐标一致。
11. 路由覆盖：显式路径不受 flow ECMP、oblivious spray 或 ecmp_rr 改写。
12. 服务器转发：`src_local -> fabric -> dst_local` 严格串行，跳过和 trigger 语义正确。
13. 源路由负例：错误端点、跨 plane、越界 bundle、错误 relay 和 compute route 被拒绝。
14. workload generator：H100 默认理论 cost、JSON theoretical/profiled 二选一、
    空 profiling 拒绝、barrier lowering、共享 payload policy、NCCL no-dedup、
    DeepEP 两级去冗余/分层传输、EPLB 官方 placement 对拍、MoonEP per-server replica，以及
    每 GPU compute/communication 双 stream lowering。
15. 生成物集成：普通 overlap、NCCL direct、DeepEP hierarchy transport、EPLB
    steady-state、MoonEP+DeepEP scale-out 和 two-stream double-buffer DAG 均由
    HTSim 加载并完成；多层 wavefront 必须实际出现下一层 MB0 Attention
    与上一层 MB1 Combine overlap。
16. MpRail 可视化：五类链路解析、跨 plane 拒绝、四行七面板 PNG、endpoint
    utilization/headroom、summary 和 inventory。
17. DAG 时间线可视化：task map/log join、每 task FCT/bytes、每 GPU
    Compute/TX/RX、计算通信 overlap、HTML/CSV/JSON 和不完整日志拒绝。
18. DSV3 两层四算法集成：两个代表性 MoE layer、双 microbatch、
    NCCL/DeepEP/EPLB/MoonEP、EP32 单 plane 拓扑、跨层依赖、计算通信
    overlap、可折叠对比 HTML 和每个算法的 MpRail 链路负载图。

执行入口：

```bash
python3 tests/run_mprail_functional.py
python3 tests/run_mprail_routing_modes.py
python3 tests/run_mprail_source_routing.py
python3 tests/run_workload_generator.py
python3 tests/run_mprail_visualization.py
python3 tests/run_dag_timeline_visualization.py
python3 tests/run_dsv3_2layer_algorithms.py
# 仅在明确要求“完整测试”时执行：
python3 tests/run_dsv3_2layer_algorithms.py --full --workers 4
```

七个入口分别验证基础拓扑/DAG、普通 flow 的物理负载均衡、显式路径与服务器内部
转发、Python workload generator、MpRail 链路负载可视化、DAG 执行时间线，以及
DSV3 两层 EP32 四算法集成案例。
每个入口独立构建或复用同一个 `htsim_uec`，但日志目录互不覆盖。

### 3.1 Smoke 与完整测试契约

`run_dsv3_2layer_algorithms.py` 默认是功能回归，不是性能实验：

| 模式 | 触发方式 | token/rank/microbatch | chunk token | 链路采样 |
|---|---|---:|---:|---:|
| smoke | 默认 | 2 | 32 | 1 us |
| full | 显式 `--full` | 4096 | 4096 | 100 us |

只有用户明确说“完整测试”时才运行 `--full`。普通修改、功能验证和
回归均使用默认 2-token smoke，避免把长时间仿真当成必选步骤。

两种模式都必须对所选算法同时完成以下三项，不允许只保留 HTSim log：

1. HTSim DAG 仿真；
2. DAG Compute/TX/RX HTML timeline；
3. 同一次 HTSim run 的 MpRail 链路负载 PNG 和 CSV。
4. 仅包含总览、timeline 和链路负载产物的 `dsv3_visualization_bundle.zip`。

四算法使用独立进程并行执行。总览 `dsv3_algorithm_comparison.html` 通过相对
路径加载各算法 timeline 和链路图；对外下载使用可视化 ZIP，不需要携带整个
run 目录。ZIP 校验成功后删除 run 目录中的全部散装 HTML；其他仿真、CSV、
JSON 和 PNG 产物仍保留。

### 3.2 NCCL、EPLB 与 MoonEP 算法验收

workload generator 入口还必须覆盖：

1. 同一 token 的两个 top-k expert 落到同一目标 rank 时，NCCL 保留两份 hidden
   payload，开启 rank-level 去冗余的算法只保留一份。
2. 相同 `(src_rank, dst_rank)` route 可以聚合为 flow，但聚合字节仍等于 route
   multiplicity 乘单 route payload。
3. NCCL dispatch/combine 均直接使用真实目标 rank，不生成 `server_forward`。
4. EP32 专用拓扑上的 `src=0, dst=8` 不经过 Spine；`src=0, dst=9` 必须经过
   L1 Spine。
5. NCCL 与 DeepEP 对照使用相同 routing assignments、expert placement、dtype
   和 chunk 参数，并分别核对 fabric RDMA、server-local 和 cross-rail 字节；不能
   用包含 local fanout/reduce 的逻辑总字节代替 fabric 字节。
6. NCCL 完整 DAG 能在 plane=1、400 Gbps 的 EP32 专用拓扑中加载并完成。
7. EPLB hierarchical `phy2log` 与官方 README 示例逐项一致。
8. EPLB 每 rank 的 physical slot 数相等，热点 route 经 replica selector 分散；稳态
   DAG 不包含 planner、migration 或 invocation-level weight prefetch。
9. EPLB token dispatch/combine 复用 DeepEP 两级去冗余和显式 hierarchy legs，完整 DAG
   能由 HTSim 加载并完成。
10. MoonEP 按 expert home server 独立 balance，replica 不跨服务器。
11. MoonEP expert prefetch 只走 local FullMesh，跨服务器 token dispatch/combine
   使用 DeepEP hierarchical transport。
12. MoonEP EP32 完整 DAG 能由 HTSim 加载并完成。
13. EP32 smoke/full 的四个 timeline 必须全部展示 rank 0-31；只画 server 0
    的 `0-7` 只能作为独立调试产物，不能进入统一可视化 ZIP。

## 4. 成功标准

- Python 进程返回 0。
- 对旧 MpRail 测试，`汇总.json` 中所有 case 为 `passed`；对 workload generator，
  `summary.json` 中所有 case 为 `passed`。
- `测试说明.md` 或 `测试报告.md` 包含实际测量值，不只写“通过”。
- 每个 flow 的日志可恢复 source、destination、plane、rail 和 spine。
- 测试失败时保留运行目录，不删除现场。
